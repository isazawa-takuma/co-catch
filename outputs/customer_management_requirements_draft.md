# 顧客管理ツール 要件定義ドラフト

作成日: 2026-07-12  
参考資料: 営業リスト - オペナビ営業リスト_神奈川_参考.csv

## 1. 目的

体験事業者への営業進捗と顧客情報を一元管理し、「いつ」「誰が」「どの事業者に」「どのようなアクションを行い」「現在どういう状況なのか」を社内で把握できるようにする。

本ツールの主目的は、営業の進捗管理と顧客管理である。リスト作成・調査管理は補助的な位置づけとし、初期版ではCSVインポートによって顧客リストを取り込み、取り込み後の営業活動を管理することを重視する。

## 2. 前提

| 項目 | 内容 |
|---|---|
| 管理単位 | 事業者単位 |
| 利用範囲 | 社内利用のみ |
| 利用人数 | 20人未満 |
| 初期対応ファイル | CSV |
| 初期画面 | トップ、一覧、詳細 |
| 初期目的 | 顧客リストの取り込み、営業進捗管理、架電・対応履歴管理 |
| ログイン | 初期開発・ローカル確認時は後回し。将来的に導入 |
| データ保存先 | DB前提 |

## 3. 想定ユーザー

- 営業担当者
- 営業管理者
- 顧客リストの取り込み・更新担当者

初期版では社内利用のみを想定し、顧客側に公開する画面や機能は含めない。

## 4. 管理対象データ

### 4.1 顧客・事業者情報

管理単位は事業者とする。店舗名や体験内容は事業者に紐づく補足情報として扱い、初期版では店舗単位・体験単位の独立した管理は行わない。

| 項目 | 内容 | 参考CSV列 |
|---|---|---|
| 顧客ID | CRM内で一意に管理するID | 新規生成 |
| 登録日 | リスト登録日 | 登録日 |
| 事業者名 | 会社名・屋号・施設名 | 事業者名 |
| 都道府県 | CSVの `地域` 列に入っている県名 | 地域 |
| 店舗・エリア名 | 市区町村、駅周辺などの補足 | 店舗 |
| 住所 | 郵便番号を含む所在地 | 住所 |
| HP URL | 公式サイトURL | HP_URL |
| 電話番号（本社） | 本社・代表電話 | 電話番号（本社） |
| 電話番号（OTA公開） | OTA等に公開されている電話番号 | 電話番号（OTA公開） |
| 担当者電話番号 | 事業者側の担当者に直接つながる電話番号 | 初期CSVにはなし。営業活動中に登録 |
| 事業者規模 | 1店舗、複数店舗、個人、未定など | 事業者規模 |
| 店舗数 | 複数店舗の場合の店舗数 | 店舗数 |

### 4.2 体験・OTA情報

体験・OTA情報は営業判断に使う補足情報として顧客詳細画面に表示する。

| 項目 | 内容 | 参考CSV列 |
|---|---|---|
| 体験内容 | 掲載中または営業対象の体験プラン内容 | 体験内容 |
| 国内掲載OTA | じゃらん、楽天トラベル、アソビュー、Activity Japan等 | 国内掲載OTA |
| OTA URL | OTAごとの掲載URL。`OTA名: URL` の形式を分解して管理する | OTA_URL（メイン4社） |
| その他OTA名 | Viator、いこーよ等 | その他OTA名 |
| 営業日数 | 月間営業日数 | 営業日数(1ヶ月) |
| リクエスト予約 | リクエスト予約可否 | リクエスト予約 |
| 備考 | 調査メモ・営業判断材料 | 備考 |

### 4.3 営業管理情報

営業進捗の中心になる情報として管理する。

| 項目 | 内容 | 備考 |
|---|---|---|
| ステータス | 現在の営業進捗 | 最新の架電・対応履歴から自動反映。履歴がない場合は顧客初期値を表示 |
| 担当者 | 現在の営業担当者 | 社内ユーザーから選択 |
| 最終アクション日 | 最後に電話・メール・商談などを行った日 | 活動履歴から自動更新 |
| 最終アクション内容 | 最後に行った活動の概要 | 活動履歴から表示 |
| 次回アクション日 | 次に対応すべき日 | 任意 |
| 次回アクション内容 | 次に行う予定の対応 | 任意 |
| 優先度 | 高/中/低など | 初期版では一覧非表示。将来必要になったら追加検討 |
| 営業メモ | 営業活動中のメモ | 参考CSVの `メモ` とは別に、ツール内で新規管理 |

### 4.4 CSVから取り込まない列

参考CSVのうち、以下の列は初期版では画面表示・管理対象から除外する。

| CSV列 | 扱い |
|---|---|
| No | 取り込まない。CRM側で顧客IDを自動採番する |
| メモ | 取り込まない。営業活動メモはツール内で新規管理する |

## 5. ステータス設計案

営業進捗は、シンプルに以下の状態で管理する。

| ステータス | 意味 |
|---|---|
| 未対応 | まだ営業アクションをしていない |
| 連絡済み | 電話・メール等で一度連絡済み |
| やり取り中 | 相手と継続的にやり取りしている |
| アポイント | 商談や打ち合わせの予定がある |
| 商談中 | 商談・提案を進めている |
| 契約 | 契約・導入が決定した |
| 失注 | 導入見込みなし |

ステータスは、架電・対応履歴の最新履歴に登録されたステータスを現在ステータスとして扱う。詳細画面や一覧画面では現在ステータスを表示し、ステータスを変更したい場合は新しい架電・対応履歴を登録する。

一覧画面・詳細画面では、ステータスごとに色付きラベルで表示する。

| ステータス | 色 |
|---|---|
| 未対応 | 灰色 |
| 連絡済み | 青色 |
| やり取り中 | 水色 |
| アポイント | 黄色 |
| 商談中 | 紫色 |
| 契約 | 緑色 |
| 失注 | 赤色 |

## 6. 初期版の画面要件

### 6.1 トップ画面

トップ画面は、各サービスの顧客管理画面へ遷移するためのシンプルなサービス選択画面とする。

今後、オペナビ以外にも「送客」など別サービスの顧客管理が必要になる想定のため、トップ画面は拡張性を重視する。営業状況の指標表示はトップ画面には置かず、各サービス配下の営業ダッシュボードで扱う。

画面構成:

- 中央にサービス選択ボタンを配置する
- 初期版では `オペナビ` と `送客` のボタンを表示する
- `オペナビ` ボタンを押すと、これまで要件定義しているオペナビ顧客一覧画面へ遷移する
- `送客` ボタンは将来拡張用の入口とする

表示項目:

| 項目 | 内容 |
|---|---|
| オペナビ | オペナビ顧客管理の入口 |
| 送客 | 送客サービス顧客管理の入口。初期版では将来拡張用 |

操作:

- `オペナビ` ボタンをクリックすると、オペナビ顧客一覧画面へ遷移する
- `送客` ボタンをクリックすると、`送客機能は準備中です` と表示する

### 6.2 オペナビ画面共通レイアウト

オペナビボタン押下後は、オペナビ配下の業務画面に遷移する。初期表示は顧客一覧画面とする。

画面構成:

- 左側にオペナビ用サイドバーを配置する
- サイドバーには `一覧画面` と `営業ダッシュボード` の項目を表示する
- サイドバーは開閉できる
- サイドバーを閉じた場合も、アイコンや最小幅表示などで再度開けるようにする

ナビゲーション:

| 項目 | 遷移先 |
|---|---|
| 一覧画面 | オペナビ顧客一覧画面 |
| 営業ダッシュボード | オペナビ営業ダッシュボード |

### 6.3 一覧画面

顧客を検索・絞り込みし、営業対象を確認する画面とする。

画面構成は、添付ラフをもとに以下の3エリアを基本とする。

- 左側: ステータスや担当者などの絞り込みメニュー
- 上部: 検索欄と主要条件チップ
- 中央: 顧客一覧テーブル

表示項目:

| 項目 | 備考 |
|---|---|
| 登録日 | CSVの登録日を表示 |
| 事業者名 | クリックするとサイドモーダルで詳細を表示 |
| 詳細リンク | 別タブで詳細画面を開くためのリンクまたはアイコン |
| 都道府県 | CSVの `地域` 列を都道府県として表示 |
| 店舗・エリア名 | 市区町村など |
| 掲載OTA数 | 掲載しているOTA数を表示。例: `3件` |
| リクエスト予約 | ○/△/× |
| ステータス | 営業進捗 |
| 担当者 | 現在の担当者 |
| 最終アクション日 | 活動履歴から表示 |
| 次回アクション日 | 対応予定日 |
| 優先度 | 初期版では非表示 |

一覧画面では電話番号を表示しない。電話番号は詳細画面で確認・コピーする。

表示仕様:

- 事業者名列は左固定にする
- 列が横に多い場合は、一覧テーブル内で横スクロールできるようにする
- 担当者が空の場合は `未担当` と表示する
- 次回アクション日が空の場合は `未設定` と表示する
- ステータスが `失注` の場合の次回アクション日表示は、今後検討する
- 日付は `YYYY/MM/DD` 形式で表示する
- データ読み込み中は `読み込み中...` と表示する

表示列の優先順位:

画面幅が狭い場合や表示列を絞る場合は、以下を優先して表示する。

1. 事業者名
2. 都道府県
3. ステータス
4. 担当者
5. 次回アクション日

スマートフォン表示では、最低限 `事業者名`、`都道府県`、`ステータス`、`担当者`、`次回アクション日` を表示する。

一覧画面では、可読性を優先するため、初期版では最新メモ・最終対応メモは表示しない。

検索・絞り込み:

- 複数条件を同時に指定できる
- 複数条件を指定した場合は、原則としてAND条件で絞り込む
- 例: `都道府県 = 神奈川県` かつ `担当者 = 山田` の顧客だけを表示する
- 事業者名検索
- 都道府県での絞り込み
- 住所検索
- 体験内容検索
- 店舗・エリア名での絞り込み
- ステータス絞り込み
- 担当者絞り込み
- OTA掲載有無での絞り込み
- 掲載OTA数での絞り込み
- リクエスト予約可否での絞り込み
- 次回アクション日での絞り込み
- 未担当のみ表示

検索欄:

- フリーワード検索を設置する
- 検索対象は、事業者名、都道府県、住所、店舗・エリア名、体験内容、備考とする
- 検索結果件数を表示する
- フリーワード検索と左側フィルター、条件チップは同時に利用できる

条件チップ:

- よく使う条件を上部にチップ形式で表示する
- 例: `未対応`、`本日対応`、`期限切れ`、`未担当`、`OTA掲載あり`
- チップを押すと一覧が絞り込まれる
- 選択中の条件は視覚的に分かるようにする

左側フィルター:

- ステータス
- 担当者
- 都道府県
- 掲載OTA数
- リクエスト予約
- 次回アクション日
- 優先度は初期版では非表示。将来検討

並び替え:

- 登録日で並び替えできる
- 最終アクション日で並び替えできる
- 次回アクション日で並び替えできる
- 掲載OTA数で並び替えできる
- ステータスで並び替えできる
- 初期表示は登録日降順とする
- ユーザーは次回アクション日昇順を選択できる

行の警告表示:

- 次回アクション日が今日の顧客は、赤色ラベルで目立たせる
- 次回アクション日を過ぎている顧客は、赤色ラベルで目立たせる
- 赤色ラベルの文言は `本日対応`、`期限切れ` などとする

一覧画面では対応しないこと:

- 検索条件の保存
- 最新メモ・最終対応メモの一覧表示
- 一覧画面からの削除
- 一括削除

操作:

- 事業者名をクリックすると、一覧画面の右側にサイドモーダルを開き、事業者詳細を確認できる
- サイドモーダルを開くクリック範囲は事業者名のみとし、行全体クリックでは開かない
- 事業者名の横に、別タブで詳細画面を開くリンクまたはアイコンを配置する
- スマートフォンではサイドモーダルではなく、画面全体で詳細を表示する
- サイドモーダルを閉じても、検索条件、フィルター、並び替え条件、ページ番号、表示件数、スクロール位置を保持する
- 別タブで詳細画面を開いた場合も、一覧画面側の検索条件、並び替え条件、ページ状態は維持する
- CSVインポートを開始できるボタンを配置する
- CSVインポートボタンを押すと、一覧画面上にポップアップを表示する
- CSVインポートが成功した場合は検索条件を維持したままポップアップを閉じ、一覧画面上部に `〇〇.csvのインポートに成功しました` と表示する
- 担当者、次回アクション日を一覧上で直接編集できる
- 一覧上で直接編集できる項目は、初期版では `担当者`、`次回アクション日` の2つに限定する
- 複数行をチェックボックスで選択し、選択した顧客の担当者を一括設定できる
- 担当者の一括設定後は検索条件、並び替え条件、ページ状態を維持したまま一覧へ戻り、更新件数を表示する
- 一覧上で直接編集した内容は、変更した時点で即保存する
- 即保存に成功した場合は、小さい成功通知を表示する
- 即保存に失敗した場合は、小さい失敗通知を表示し、再編集できるようにする
- 一覧上のステータスは、最新の架電・対応履歴から反映された現在ステータスを表示する
- 次回アクション日は、詳細画面からも確認できるが、主な編集場所は一覧画面とする
- 検索条件、フィルター、条件チップをまとめて解除できる `条件をクリア` ボタンを配置する
- 1ページあたりの表示件数を選択できる
- 表示件数は `25件`、`50件`、`100件` から選択できる
- 一覧はページネーションで移動できる
- CSVエクスポートは初期版では実装せず、後々で検討する

同時編集時の扱い:

- 同じ顧客を複数人が同時に編集した場合は、最後に保存された内容を反映する
- 初期版では厳密な競合制御やロックは行わない

### 6.4 営業ダッシュボード

営業ダッシュボードは、オペナビの営業状況を数値で把握する画面とする。トップ画面ではなく、オペナビ配下のサイドバーから遷移する。

表示指標:

| 指標 | 意味 |
|---|---|
| 総顧客数 | 登録されている事業者数 |
| 未対応件数 | ステータスが未対応の件数 |
| 本日対応件数 | 次回アクション日が今日の件数 |
| 期限切れ件数 | 次回アクション日が過去の件数 |
| 未担当件数 | 担当者が未設定の件数 |
| 契約件数 | ステータスが契約の件数 |
| 失注件数 | ステータスが失注の件数 |

操作:

- 各指標をクリックすると、該当条件で絞り込まれた一覧画面へ遷移できると望ましい
- 例: `未対応件数` をクリックすると、ステータス `未対応` で絞り込んだ一覧画面を表示する

### 6.5 詳細画面

事業者ごとの顧客情報と営業活動を管理する画面とする。

画面構成は、添付ラフをもとに以下の3ブロックを基本とする。

- 上部左: 事業者の基本情報
- 上部右: 体験内容、OTA、店舗数などの営業判断情報
- 下部: 架電・対応履歴のテーブル

表示ブロック:

| ブロック | 内容 |
|---|---|
| 基本情報 | 電話番号、担当者電話番号、事業者名、Web URL、住所、登録日 |
| 営業判断情報 | 体験内容、OTA、店舗数、営業日数、リクエスト予約、備考 |
| 営業管理 | 現在のステータス、担当者、最終アクション、次回アクション |
| 架電・対応履歴 | 日付、名前、担当者、ステータス、メモ |
| 新規履歴登録 | 架電・対応内容を登録するフォーム |

詳細画面の主要表示項目:

| 項目 | 表示位置 | 備考 |
|---|---|---|
| 登録日 | 上部左の後半 | CSVの `登録日` を表示する。先頭項目にはせず、基本情報の後ろ側に配置する |
| 電話番号（本社） | 上部左 | 電話番号（OTA公開）と同じ扱いで表示する。横にワンクリックコピー用のボタンを配置する |
| 電話番号（OTA公開） | 上部左 | 電話番号（本社）と同じ扱いで表示する。横にワンクリックコピー用のボタンを配置する |
| 担当者電話番号 | 上部左 | 事業者側担当者の直通・携帯など。横にワンクリックコピー用のボタンを配置する |
| 事業者名 | 上部左 | 画面内で最も目立つ情報にする |
| Web URL | 上部左 | URLを編集できる。入力欄の右側に公式サイトを別タブで開くリンクを配置する |
| 住所 | 上部左 | 必要に応じてコピーできる |
| 体験内容 | 上部右 | 参考CSVの `体験内容` を表示 |
| OTA | 上部右 | じゃらん、楽天、アソビュー等のOTA名をリンク表示する。例: `じゃらん` の文字を押すと該当URLを開く |
| 店舗数 | 上部右 | 参考CSVの `店舗数` を表示 |
| ステータス | 上部または営業管理欄 | 最新の架電・対応履歴から反映された現在ステータスを表示する |
| 担当者 | 上部または営業管理欄 | 社内担当者を表示・変更できる |
| 架電・対応履歴 | 下部 | 最新順で表示する |

架電・対応履歴テーブル:

| 列 | 内容 |
|---|---|
| 日時 | 対応した日時 |
| 名前 | 社内の対応者 |
| 担当者 | 電話・商談で対応した相手。名前が分からない場合は空欄可 |
| 担当ステータス | 相手の立場。`受付`、`担当者`、`代表`、`その他` から選択 |
| ステータス | 対応後のステータス |
| メモ | 会話内容、次にやること、温度感など |

操作:

- ステータスは架電・対応履歴の新規登録によって更新できる
- 担当者を変更できる
- 次回アクション日・内容を登録できる
- 電話番号、HP URL、OTA名リンクをクリックできる
- 電話番号（本社）、電話番号（OTA公開）、担当者電話番号をワンクリックでコピーできる
- 電話番号コピー後は `コピーしました` と小さい通知を表示する
- HP URL、OTA名リンクなどの外部リンクは別タブで開く
- 架電・対応履歴を登録できる
- 営業メモを登録・編集できる
- 詳細画面で編集した内容は保存時に小さい成功/失敗通知を表示する
- 成功通知はサーバー側でDB保存処理が完了した後に表示する
- 保存が完了しなかった場合は成功通知を表示せず、失敗通知を表示して再編集できるようにする
- サイドモーダル内で未保存の変更がある状態で閉じようとした場合は、保存していない変更があることを確認するポップアップを表示する
- 顧客を削除できる
- 削除ボタン押下時は確認モーダルを表示し、`はい`、`いいえ` で削除可否を選択できる
- 削除方式は論理削除とし、DB上は `deleted_at` を記録する
- 論理削除済みの顧客は、一覧画面に表示しない
- 論理削除済みの顧客は、通常検索の対象に含めない
- 削除は初期版では詳細画面からのみ行う
- 一覧画面からの削除、一括削除は初期版では行わない
- 一覧画面から開くサイドモーダルでも詳細画面と同じ編集ができる
- ただし、顧客削除はサイドモーダルでは行わず、別タブの詳細画面からのみ行う
- 詳細画面およびサイドモーダルには `戻る`、`次へ` ボタンを表示し、前後の事業者詳細へ移動できる
- サイドモーダル内で `戻る`、`次へ` を押した場合は、サイドモーダルを開いたまま詳細内容を切り替える
- 未保存の変更がある状態で前後移動しようとした場合は、移動前に確認する

## 7. 営業活動履歴の要件

顧客ごとに、架電・対応履歴を時系列で残す。初期版では架電結果の専用選択肢は設けず、ステータスとメモで管理する。

登録項目:

| 項目 | 内容 |
|---|---|
| 日時 | 電話・メール・商談などを行った日時。詳細画面またはサイドモーダルを開いた時点の現在日時を自動入力する |
| 名前 | 対応した社内担当者 |
| 担当者 | 電話・商談した相手の名前や役職。任意入力 |
| 担当ステータス | 相手の立場。`受付`、`担当者`、`代表`、`その他` から選択。任意入力 |
| ステータス | 対応後の営業ステータス |
| メモ | 会話内容、温度感、次にすべきこと |

必須項目:

- 日時
- 名前
- ステータス
- メモ

任意項目:

- 担当者
- 担当ステータス

活動履歴の登録により、顧客の `最終アクション日`、`最終アクション内容`、`ステータス` を最新履歴の内容で自動更新する。登録済み履歴のメモを更新した場合は、最新履歴のメモ内容に応じて `最終アクション内容` を再同期する。

履歴の編集・削除:

- 登録済みの架電・対応履歴はメモのみ編集できる
- 日時、名前、担当者、担当ステータス、ステータスは登録後に画面上では編集しない
- 登録済みの架電・対応履歴は初期版では削除できない
- 現在ステータスは最新の架電・対応履歴と一致させる
- 詳細画面や一覧画面では、ステータスだけを独立して変更しない

## 8. CSVインポート要件

初期版では参考CSV形式の取り込みに対応する。

CSVインポートは、一覧画面のCSVインポートボタンから開くポップアップ内で行う。ファイルダウンロードからインポート実行までをポップアップ内で完結させる。

要件:

- 一覧画面のCSVインポートボタンを押すとポップアップを表示する
- ポップアップ内でCSVテンプレートをダウンロードできる
- CSVファイルをアップロードできる
- 文字コードはUTF-8を想定する
- インポート前にプレビューできる
- 取り込み対象列と除外列を確認できる
- インポート前に必須列の存在チェックを行う
- 必須列が不足している場合は取り込みを開始せず、ポップアップ内に不足している列名をエラー表示する
- 必須値が空の行がある場合は、該当行と不足項目をポップアップ内にエラー表示する
- 必須値エラーがある場合は、該当行を取り込まない
- `OTA_URL（メイン4社）` は、行内の `OTA名: URL` を分解して取り込む
- 複数行で記載されたOTA URLは、OTAごとに別データとして保持する
- 取り込みエラーを行単位で確認できる
- 既存顧客との重複を検出できる
- 重複時は確認画面を表示し、ユーザーが処理方法を選べるようにする
- インポート成功時はポップアップを閉じ、一覧画面上部に成功メッセージを表示する
- 成功メッセージにはインポートしたCSVファイル名を含める

ポップアップ内の流れ:

1. CSVテンプレートをダウンロードする
2. CSVファイルを選択する
3. プレビューとチェック結果を確認する
4. エラーがなければインポートを実行する
5. 成功時は一覧画面に戻り、成功メッセージを表示する

成功メッセージ例:

`opnavi_kanagawa.csvのインポートに成功しました`

必須列:

| 必須列 | 用途 |
|---|---|
| 登録日 | リスト登録日の管理 |
| 事業者名 | 顧客名として必須 |
| 地域 | CSV上の列名。画面上では都道府県として表示・検索・絞り込みに使用 |
| 店舗 | 店舗・エリア名として使用 |
| 住所 | 顧客情報、重複判定に使用 |
| 電話番号（OTA公開） | 主要連絡先候補 |
| 体験内容 | 営業判断情報として使用 |
| 国内掲載OTA | 掲載OTA数の算出に使用 |
| 営業日数(1ヶ月) | 営業判断情報として使用 |
| リクエスト予約 | 営業判断情報として使用 |
| OTA_URL（メイン4社） | OTA名リンク生成に使用 |
| ステータス | 営業進捗管理に使用 |
| 担当者 | 担当管理に使用 |

必須列不足時のエラー表示例:

`CSVの必須列が不足しています: 事業者名, 地域, OTA_URL（メイン4社）`

必須値:

以下の項目は、列が存在するだけでなく値が空でないことを必須とする。

| 必須値項目 | 空の場合の扱い |
|---|---|
| 登録日 | エラー |
| 事業者名 | エラー |
| 地域 | エラー |
| 店舗 | エラー |
| 住所 | エラー |
| 体験内容 | エラー |
| 国内掲載OTA | エラー |
| 営業日数(1ヶ月) | エラー |
| リクエスト予約 | エラー |

営業日数による取り込み条件:

- `営業日数(1ヶ月)` が12日未満の行は、インポート対象外としてスキップする
- 12日未満の行があっても、他の正常な行はインポートする
- インポート成功後、一覧画面上部にスキップ件数と対象行を表示する

空行の扱い:

- `No` やスコア計算用の列に値が残っていても、登録日・事業者名・住所などインポート対象項目がすべて空の行は空行として無視する
- 一部のインポート対象項目だけ空の場合は、従来どおり必須値不足エラーとして扱う

必須値不足時のエラー表示例:

`3行目: 事業者名が空です`

`8行目: 国内掲載OTA, 営業日数(1ヶ月) が空です`

`ステータス` と `担当者` は列としては必要だが、値が空でもインポート可能とする。空の場合は、インポート後に一覧画面で編集する。

OTA URL取り込み例:

| CSV内の記載 | 画面表示 |
|---|---|
| `じゃらん: https://...` | `じゃらん` という文字にURLをリンクする |
| `楽天トラベル: https://...` | `楽天トラベル` という文字にURLをリンクする |
| `アソビュー！: https://...` | `アソビュー！` という文字にURLをリンクする |

重複判定キー:

- 初期版では `事業者名 + 住所` の組み合わせで重複判定する

補足:

- 電話番号やHP URLは、表記揺れや未入力があるため初期版の主キーにはしない
- 重複データが見つかった場合は確認画面を表示する
- 上書き時、既存顧客のステータスはCSVでは更新しない。現在ステータスは最新の架電・対応履歴から反映するため、CSVの `ステータス` は新規作成時の初期値としてのみ使用する

## 11. データモデル案

DBはリレーショナルDBを前提とする。バックエンドは `Laravel + MySQL` を基本方針とする。ローカル開発ではDocker Desktop上でLaravel、MySQL、Webサーバーを動かす。

理由:

- 顧客、担当者、活動履歴、OTAリンクを関連付けて管理しやすい
- 複数条件検索、並び替え、ページネーションに向いている
- 論理削除、バックアップ、将来のサービス追加に対応しやすい
- Laravel/PHPとの組み合わせで利用実績が多く、保守しやすい

技術構成方針:

| 項目 | 方針 |
|---|---|
| バックエンド | Laravel |
| 言語 | PHP |
| DB | MySQL |
| ローカル環境 | Docker Desktop |
| 開発時ログイン | 開発用の固定ユーザーで自動ログイン扱い |
| 本番想定 | エックスサーバー上にLaravelアプリとして配置する想定 |

ローカル開発ではDockerを使うが、本番のエックスサーバーでDockerを使う前提にはしない。Dockerは開発環境を揃えるために利用し、本番公開時はエックスサーバーのPHP/MySQL環境に合わせてデプロイする。

送客サービスはオペナビとは別データとして分ける。トップ画面だけ共通とし、データと画面はサービス別にする。

サービス分離方針:

- オペナビと送客はDB上も別テーブルとして分離する
- 初期版ではオペナビ用のテーブルを作成する
- 送客サービス追加時は、送客用の顧客・履歴テーブルを別途設計する
- 共通化しすぎず、サービスごとの業務フロー差分を吸収できるようにする

### 11.5 検索・絞り込み向け設計

一覧画面では複数条件検索を行うため、検索・絞り込みでよく使う項目はDB上で検索しやすい形にしておく。

- `customers.next_action_at`

- `customers.request_booking_status`

一覧取得APIは、以下のような検索条件を受け取れる設計にする。

| パラメータ | 内容 |

## 12. 権限案

利用人数は20人未満の社内利用のため、初期版では権限による編集制御は行わない。

| 利用者 | できること |
|---|---|
| 社内ユーザー | 全顧客の閲覧・編集、CSVインポート、活動履歴登録、ステータス更新 |

初期版では、全員が全顧客を閲覧・編集できる前提とする。変更履歴は初期版では必須にしないが、誰が何を変更したかを追跡したくなった場合に追加検討する。

ログイン機能:

- ログイン機能は必要だが、初期開発・ローカル確認時は後回しにする
- 実装確認時に毎回ログインを求められないよう、初期版では開発用の固定ユーザーで自動ログイン扱いにする
- 実運用に入るタイミングでは、社内ユーザーでログインできるようにする
- ログインの詳細仕様は実装時に検討する
- 担当者はログイン有無に関わらず、ユーザー一覧から選択する

バックアップ・復元:

- 顧客データは戻せるようにする
- DBの定期バックアップを前提とする
- バックアップ頻度は日次とする
- CSVインポート前や大きなデータ更新前に、手動バックアップを取れるようにする
- 論理削除済みデータは `deleted_at` により復元できる余地を残す
- 初期版では、管理者向けの画面復元機能までは必須にしない

バックアップ時の懸念点:

- 日次バックアップの場合、当日中の変更はバックアップ前だと復元できない可能性がある
- 復元すると、復元時点以降に登録・更新されたデータが巻き戻る可能性がある
- CSVインポート直後に不具合が見つかった場合、インポート前の状態に戻す手段が必要になる
- バックアップファイルの保存場所と保存期間を決める必要がある
- 個人情報や電話番号を含むため、バックアップファイルの閲覧・取得権限に注意する

初期案:

- DB全体を日次でバックアップする
- バックアップ保存期間は30日を目安にする
- CSVインポート前に手動バックアップを実行できるようにする
- 復元は初期版では開発者または管理者が対応する

セキュリティ:

- 顧客情報、電話番号、担当者電話番号、活動履歴メモを保護対象とする
- 本番環境ではHTTPSで通信を暗号化する
- DB接続情報はソースコードに直接書かず、環境変数などで管理する
- DBユーザーには必要最小限の権限のみ付与する
- バックアップファイルは暗号化、またはアクセス制限された場所に保存する
- バックアップファイルには電話番号などの情報が含まれるため、閲覧・取得できる人を制限する
- ログに電話番号、担当者電話番号、メモ全文などの機微情報を出力しない
- 将来的にログイン機能を入れる場合、パスワードは平文保存せずハッシュ化する
- DB内の電話番号などを項目単位で暗号化するかは、運用環境と実装コストを踏まえて検討する

暗号化方針:

- 通信: HTTPSで暗号化する
- バックアップ: 暗号化または厳格なアクセス制限を行う
- DB保存: まずはDBサーバー・ファイル・権限管理で保護し、必要に応じて電話番号などのカラム暗号化を検討する

## 14. 懸念点・今後検討事項

実装時の細かいUI調整ではなく、運用・設計上の懸念点として以下を残す。

| 項目 | 内容 | 初期版での扱い |
|---|---|---|
| サービス分離 | オペナビと送客をどこまで共通化するか | トップだけ共通。データと画面はサービス別 |
| DB分離 | オペナビと送客を同一テーブル内のサービス区分で分けるか、別テーブルにするか | 別テーブル方針 |
| ログインなし期間の担当者管理 | 初期版では実際に誰が更新したかを厳密に追えない可能性がある | 初期版では許容。実装時にはログイン導入を検討 |
| 個人情報・電話番号の閲覧範囲 | 電話番号やメモを誰が見られるか | 初期版では社内ユーザー全員が閲覧可能 |
| CSV上書き事故 | 重複データの上書き時にどの項目を更新するか | 後で決める。確認画面は用意する |
| 削除データの復元 | 論理削除した顧客を画面から復元できるか | 初期版では復元画面なし。開発者/管理者対応 |
| バックアップ復元テスト | バックアップが実際に復元できるか | 運用前に一度は復元テストを行う |
| カラム単位暗号化 | 電話番号などをDB内で個別暗号化するか | 初期版ではHTTPS、DB権限、バックアップ保護を優先。必要に応じて検討 |
| 送客サービス追加時の設計 | 送客がオペナビと異なる業務フローになる可能性 | 送客追加時に別途要件定義する |

## 15. 非機能要件

- PCブラウザで使いやすいことを優先する
- スマートフォンでは最低限の列表示と詳細確認ができるようにする
- スマートフォンで詳細を開く場合は、サイドモーダルではなく画面全体で表示する
- 20人未満の社内利用で安定して動作する
- データ保存はDB前提とする
- バックエンドはLaravel/PHPを基本方針とする
- DBはMySQLを基本方針とする
- ローカル開発ではDocker Desktopを利用する
- 本番のエックスサーバーではDocker利用を前提にせず、PHP/MySQL環境へ配置する
- DBバックアップにより、データを復元できるようにする
- 本番環境ではHTTPSで通信を暗号化する
- DB接続情報やバックアップファイルを適切に保護する
- 顧客一覧は数千件規模でも検索・絞り込みできる
- 複数条件検索を行っても、一覧表示が大きく遅くならないようにする
- 一覧画面はページネーションを前提にし、1ページあたりの表示件数を選択できる
- 一覧画面でサイドモーダルや別タブ詳細を開いても、検索条件、フィルター、並び替え条件、ページ番号、表示件数を保持する
- CSVインポート時に文字化けしない
- 誰がいつどの顧客に対応したか、活動履歴から追える
- 電話番号、URL、長文の体験内容、備考が画面上で崩れない
- 同時編集時は、最後に保存された内容を反映する
- 日付は画面上で `YYYY/MM/DD` 形式に統一する
