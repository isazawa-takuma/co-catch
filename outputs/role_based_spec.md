# コキャッチ 画面・機能仕様／簡易設計書

更新日: 2026-10-04

## 1. 対象・資料の位置づけ

管理者・営業担当・アポインターの3権限について、リポジトリの `app/` 配下をコードリーディングして整理した実装仕様です。画面、ルート、入力チェック、サービス、モデル、マイグレーション、既存テストを根拠としています。本番環境の配備状況・DB設定・メール到達を保証する資料ではありません。`deploy/` の配布用コピーは調査対象に含めません。

既存の[技術仕様書](technical_spec.md)には初期版の記述が含まれます。3権限の画面・認証・検索・成績については本書を現行実装の要約として参照してください。[要件定義書](customer_management_requirements_draft.md)は背景・当初要件の参照資料です。

## 2. 権限別の画面・機能比較

営業担当とアポインターは共通のユーザー画面を利用し、顧客の閲覧条件だけが異なります。「アポインター」は画面の権限選択では「アポイント」と表示されます。

| 項目 | 管理者 (`admin`) | 営業担当 (`sales`) | アポインター (`appointment`) |
|---|---|---|---|
| ログイン | `/opnavi/admin/login` | `/opnavi/user/login` | `/opnavi/user/login` |
| ログイン後 | `/opnavi/admin/customers` | `/opnavi/user/customers` | `/opnavi/user/customers` |
| 顧客一覧・詳細 | 全顧客（論理削除済みを除く） | `sales_owner_id` が本人の顧客 | `owner_id` が本人の顧客 |
| 検索・ソート | 利用可能 | 担当範囲内で利用可能 | 担当範囲内で利用可能 |
| CSV取込 | 可能 | 不可 | 不可 |
| コール担当の変更・一括設定 | 可能 | 不可 | 不可 |
| 基本情報の編集 | 管理者用更新処理 | 担当者電話番号・次回アクション日時・重要アラート・営業メモのみ | 同左 |
| 架電・対応履歴の閲覧／登録／更新 | 可能 | 担当顧客で可能 | 担当顧客で可能 |
| 履歴・顧客の削除 | 可能 | 不可 | 不可 |
| 営業担当の選択UI | APO時のポップアップ | 同左 | 同左 |
| 営業ダッシュボード | あり | なし | なし |
| ユーザー管理／他ユーザーの成績 | あり | なし | なし |
| 本人のマイページ／日次確定 | なし | あり | あり |
| パスワード変更・ログアウト | あり | あり | あり |

担当外の顧客は一覧から除外するだけでなく、詳細URLの直接アクセス・更新・履歴操作もコントローラーで制限します。担当外アクセスは通常画面では一覧へ戻してエラー表示、Ajaxでは403を返します。権限が異なる管理者／ユーザーの保護ルートへアクセスすると、ログアウトしてログイン画面へ戻します。

根拠: [ルート](../app/routes/web.php)、[顧客コントローラー](../app/app/Http/Controllers/CustomerController.php)、[権限制御](../app/app/Http/Middleware/EnsureOpnaviRole.php)。

## 3. 管理者画面

### 3.1 顧客一覧・詳細

- 顧客一覧で全顧客を検索・確認し、事業者名クリックで詳細ドロワー、別タブアイコンで独立した詳細画面を開く。
- 一覧のコール担当プルダウンから個別変更、チェックした顧客へ一括設定が可能。選択肢は有効ユーザー。
- 一覧の次回アクションは日時の表示のみ。編集は詳細画面で行う。
- 詳細では基本情報、体験情報・OTAリンク、架電・対応履歴を確認する。Webサイトを開く・電話番号コピーに対応。
- 基本情報のステータスは最新履歴から反映される表示値。営業担当のプルダウンは無効化され、APO時の選択ポップアップを使用する。
- 基本情報の「登録日」入力は非表示。登録日はDBおよび一覧の列定義に残る。
- 顧客削除は `SoftDeletes` による論理削除。履歴削除は履歴レコードを削除し、顧客ステータスを再計算する。

### 3.2 CSVインポート

- 一覧のCSVインポートモーダルからファイルを送信する。画面上の手入力による顧客新規作成フォームはない。
- 必須ヘッダー・必須値を検証し、営業日数が月12日未満の行はスキップして警告する。
- 「事業者名＋住所」で既存顧客と照合。重複候補は確認後に更新取込する。既存顧客のステータスは更新取込で上書きしない。
- OTA URLを解析し、顧客とOTAリンクを保存する。取込データの保存にはDBトランザクションを使用する。
- CSVの担当者名が未登録の場合、ユーザーレコードを自動作成する経路がある。招待画面経由のユーザー登録とは別処理。

詳細: [CustomerImportService](../app/app/Services/Opnavi/CustomerImportService.php)、[既存のCSV仕様](technical_spec.md#9-csvインポート仕様)。

### 3.3 営業ダッシュボード

URL: `/opnavi/admin/dashboard`

顧客数、未対応、本日対応、期限切れ、コール担当未設定、契約、失注を集計する。顧客単位の集計で、ユーザーの架電履歴件数とは別の指標。本日対応と期限切れは次回アクションの日付を基準にする。

根拠: [DashboardController](../app/app/Http/Controllers/DashboardController.php)。

### 3.4 ユーザー管理

URL: `/opnavi/admin/user_management`

| 操作 | 現在の動作 |
|---|---|
| 一覧 | 名前、メールアドレス、権限、状態、登録日を表示。停止中も一覧に含む |
| 追加 | モーダルでメールアドレス、編集可能なランダム初期パスワード、権限を入力 |
| 送信 | DBへユーザー作成後、ログインURL・メールアドレス・初期パスワードをメール送信 |
| メール制限 | 招待先は `@illuvia-inc.com`、登録済みメールアドレスは重複不可 |
| 再発行 | 行末の三点メニューから初期パスワードを再生成・メール送信。ユーザーIDと履歴を保持し、旧パスワードを置換 |
| 権限変更 | 別画面 `/opnavi/admin/user_management/{user}/role/edit` で選択し適用 |
| 無効化 | `is_active=false` に変更。ユーザーの物理削除は行わない |
| 自分自身 | 権限変更と無効化は非表示かつサーバー側でも拒否 |
| 架電状況 | ユーザー名クリックで `/opnavi/admin/user_management/{user}/activities` を開く |

作成・再発行のメールは同期送信。送信例外時には同じトランザクション内のユーザー作成／パスワード変更をロールバックする。実際の送信元・SMTP接続・ログインURLのホストは環境設定に依存する。

架電状況は対象ユーザーの「本日の成績」、本日の架電数、件数の多い順のステータス別件数、日付範囲内の確定済み成績を表示する。更新ボタンを備え、管理者による代理確定ボタンはない。全期間の合計架電数・事業者とメモの履歴表は表示しない。

根拠: [UserManagementController](../app/app/Http/Controllers/UserManagementController.php)、[ユーザー管理ビュー](../app/resources/views/user_management/index.blade.php)。

## 4. 営業担当画面

- ログイン後は営業担当として割り当てられた顧客だけを表示する。判定は名前文字列ではなく `sales_owner_id = ログインユーザーID`。
- コール担当が他ユーザーでも、営業担当が本人なら表示対象となる。画面の一覧列「コール担当」は、その顧客のコール担当を表示する。
- 担当顧客の基本情報・OTA情報・過去の架電履歴を閲覧し、担当者電話番号・次回アクション日時・重要アラート・営業メモを更新できる。
- 担当顧客の履歴を登録・更新し、営業活動の内容をメモとして保存できる。履歴のユーザーIDはログインユーザーに固定される。
- マイページで本人の本日成績を確認・確定し、過去の確定済み成績を期間指定で閲覧できる。

## 5. アポインター画面

- ログイン後はコール担当として割り当てられた顧客だけを表示する。判定は `owner_id = ログインユーザーID`。
- 割当は管理者が一覧または詳細から実施する。アポインター本人は担当割当を変更できない。
- 架電結果を履歴へ登録し、次回アクション日時・重要アラート・営業メモなどを更新する。
- APO成立時、営業担当未設定なら営業担当の選択ポップアップを表示し、選んだ営業担当へ引き継ぐ。
- 営業担当を設定してもコール担当は変更されないため、アポインターと営業担当の両者から顧客を閲覧できる。
- マイページの集計・確定方法は営業担当と同一。

## 6. 共通仕様

### 6.1 ログイン・初回設定

1. 管理者がユーザーを追加し、権限別ログインURLと初期パスワードをメール送信する。
2. メールアドレスとパスワードでログインする。無効アカウント・ログイン画面と異なる権限・期限切れ初期パスワードは拒否する。
3. 初期パスワード使用中、または姓・名が未設定なら `/opnavi/initial_setup` に強制遷移する。
4. 姓・名と新パスワード、確認用パスワードを設定し、権限別一覧へ遷移する。初回設定画面にはサイドバーを表示しない。

- 初期パスワードの有効期限: 作成／再発行から7日間。再発行時は期限も更新する。
- 初回設定・通常のパスワード変更: 最低8文字、英字と数字を含む、確認入力一致が必要。
- 通常変更では現在のパスワードを照合する。パスワードはハッシュ化して保存する。
- ログイン済みでログイン画面を開くと、初回設定または権限別顧客一覧へ遷移する。
- 未ログインで `/opnavi/user/...` を開くとユーザーログイン、`/opnavi/admin/...` では管理者ログインへ遷移する。
- セッションの設定既定値は20,160分（2週間の無操作期限）。環境変数で変更可能。ログインから必ず14日で切れる固定期限ではない。
- サイドバー下部のユーザー名メニューからパスワード変更・確認付きログアウトが可能。マイページのリンクは営業／アポイントのみ。ユーザー画面のブランド名はクリック不可。

根拠: [LoginController](../app/app/Http/Controllers/Auth/LoginController.php)、[初回設定制御](../app/app/Http/Middleware/EnsureInitialSetupComplete.php)、[セッション設定](../app/config/session.php)。

### 6.2 顧客一覧の検索・表示

| 条件／操作 | 仕様 |
|---|---|
| 期間 | 次回アクションの開始日・終了日。指定した両端の日を含む。片側だけでも検索可能 |
| Rank | A〜H。最新の架電履歴のRankを参照 |
| 相手担当者 | すべて／入力あり／未入力。最新履歴の `contact_person` を参照し、空白だけも未入力扱い。履歴がない顧客も未入力に含む |
| フリーワード | 事業者名・住所・営業メモ・電話番号3項目。体験内容・履歴メモは対象外 |
| AND条件 | 期間・Rank・相手担当者・フリーワードはAND。スペース区切りキーワード同士もAND |
| 文字検索 | MySQLで2文字以上はFULLTEXTの `MATCH ... AGAINST (... IN BOOLEAN MODE)` による必須フレーズ検索。1文字およびSQLiteではLIKE。パーサー指定の制約は下記参照 |
| 電話検索 | 本社・OTA公開・担当者電話番号。保存値と検索語を数字のみに正規化し、完全一致・前方・中間一致に対応 |
| 電話検索の索引 | 正規化カラムの個別INDEXと、3桁以上の連続部分文字列を格納する索引テーブル。1〜2桁はLIKEによる部分一致 |
| ソート | 掲載OTA数・最終アクション・次回アクションの列名全体をクリック。昇順→降順→デフォルト順。未選択列は「↑↓」表示 |
| デフォルト順 | 次回アクション昇順、未設定は末尾、同値は顧客ID降順 |
| 表示件数 | 検索とテーブルの間の右側に25／50／100件の選択。既定25件 |
| 画面更新 | ソートはAjaxで一覧部分を更新。検索・件数変更・マイページ更新は通常のリクエスト／再読み込み |

最新履歴の判定は `action_at` 降順、同時刻なら `id` 降順。各キーワードについて文字カラムまたは電話カラムに一致すればよく、複数キーワードが別のカラムに一致しても検索対象になる。

根拠: [CustomerQueryService](../app/app/Services/Opnavi/CustomerQueryService.php)、[電話番号正規化](../app/app/Support/PhoneSearch.php)、[一覧ビュー](../app/resources/views/customers/index.blade.php)。

### 6.3 架電・対応履歴と営業引き継ぎ

| 項目 | 仕様 |
|---|---|
| 日時 | `action_at`。新規登録で日時カレンダーを使用。既存履歴は画面上読み取り専用 |
| Rank | A、B、C、D、E、F、G、Hから選択。必須 |
| 担当者 | 相手担当者の自由入力。任意 |
| 担当ステータス | 未選択／担当外（男）／担当外（女）／担当（男）／担当（女）／社長 |
| ステータス | 下記20項目から選択。必須 |
| メモ | 必須の自由入力 |
| 登録ユーザー | 管理者の新規登録は本人、営業／アポイントの登録・更新もログイン本人。管理者の既存履歴更新は元のユーザーIDを保持 |

ステータス選択肢（表示順）:

コール、コールのみ、担不在、受付ブロック、NG、メール、メモ、情報共有、逆電、逆メール、APO、逆連絡APO、APO変更、APOキャンセル、詰め直し、HP問合せ、現アナ、初訪、再訪、対応。

- 新規登録・既存履歴の更新の両方で、ステータスが厳密に `APO` かつ営業担当未設定なら、送信を止めて営業担当選択ポップアップを表示する。
- 選択肢は有効な営業権限のユーザー。選択後、操作中の履歴フォームのみを送信する。設定済みの営業担当があればポップアップを省略する。
- サーバー側でもAPO時の営業担当を必須チェックし、顧客の `sales_owner_id` に保存する。APO変更・逆連絡APOなどはこの判定の対象外。
- 履歴保存／削除後、最新履歴から顧客ステータス、最終アクション日、メモ要約を更新する。履歴がなくなれば未対応へ戻す。
- 旧ステータスの履歴は「現在値」として表示可能。新規画面の選択肢とサーバーで受け付ける旧値は一致しない場合がある。

根拠: [履歴サービス](../app/app/Services/Opnavi/CustomerActivityService.php)、[入力チェック](../app/app/Http/Requests/ActivitySaveRequest.php)、[詳細ビュー](../app/resources/views/customers/_detail.blade.php)、[画面JS](../app/public/js/app.js)。

### 6.4 次回アクション・重要アラート・別タブ同期

- 次回アクションは年月日＋時分で設定する。カスタムカレンダーの月移動だけでは入力値を変更せず、選択・適用で確定する。
- 次回アクションでは過去の日付を選択できず、サーバーでも本日以降を検証する。同日の過去時刻を禁止するチェックはない。
- 次回アクション未設定時は重要アラートのチェック不可。日付を消した場合はアラートもオフになる。
- ログイン済みのサイドバー付き画面で通知取得を行う。5分先から直近10分前までの予定を取得し、ブラウザーのタイマーで設定日時に表示を試みる。通知取得は初回約1秒後、以後60秒間隔、タブ復帰時にも実施する。
- アラートは画面上部中央に事業者名・具体的な日時と「開く」を表示する。「開く」は対象詳細を別タブで開き、クリック時にポップアップを消して通知済み状態を保存する。
- 営業／アポイントのアラートも担当顧客のみに制限する。管理者は全顧客が対象。
- 詳細保存後、事業者名・地域・店舗・リクエスト予約・コール担当・ステータス・最終／次回アクションを一覧行へ反映する。同一オリジンの別タブ同期はBroadcastChannelとlocalStorageイベントで行う。検索結果の再抽出やソート順の自動再配置は行わない。
- ブラウザーを閉じている場合には通知しない。休止・バックグラウンド制限・端末時計のずれで表示が遅れる可能性があり、秒単位の到達保証はない。

根拠: [通知API](../app/app/Http/Controllers/CustomerController.php)、[ブラウザー側の通知・同期](../app/public/js/app.js)。

### 6.5 マイページ・日次成績

URL: `/opnavi/my_page`。営業担当とアポインターのみ利用可能。

- 「本日の成績」に本日の架電数とステータス別件数を表示する。内訳は件数の多い順、同件数は履歴ステータスの定義順。
- 1件の履歴登録を1件として数える。同一事業者へ複数登録すればその回数を加算し、メモ・情報共有などのステータスも集計に含む。事業者数や実際の発信回数を数える仕組みではない。
- 集計は `activities.user_id` と `created_at` の当日範囲（Asia/Tokyo）を使用する。履歴の対応日時 `action_at` を過去日に設定しても、今日登録すれば今日の件数となる。
- 未確定なら最新の履歴から集計。「更新」で再読み込みする。
- 「本日の成績を確定」の確認ポップアップから送信すると、その時点の合計・ステータス別件数を保存する。画面下部左に更新・確定を横並びで配置する。
- ユーザー＋日付のUNIQUE制約と `insertOrIgnore` で重複確定を防ぐ。確定後は当日ボタン無効。本日の表示も保存済み成績へ切り替える。
- 確定後に履歴を追加・更新・削除しても、確定済み成績は変更しない。再確定／取り消し画面はない。
- 「日付ごとの成績」は期間内の確定済み日だけを日付降順に表示。既定期間は当月初日〜末日。終了日が開始日より前ならエラー。
- 未確定日を自動補完する処理はない。全期間の合計数、事業者名・メモの履歴表は表示しない。
- 管理者のユーザー別架電状況も同じ集計基準を使うが、本人に代わる確定操作は提供しない。

根拠: [MyPageController](../app/app/Http/Controllers/MyPageController.php)、[マイページビュー](../app/resources/views/mypage/show.blade.php)、[日次成績テーブル](../app/database/migrations/2026_09_18_000001_create_opnavi_daily_call_results_table.php)。

## 7. 簡易設計

### 7.1 構成

Laravel 9のWebアプリケーション。Bladeで画面を描画し、`public/js/app.js` がドロワー、カレンダー、APO選択、別タブ同期、アラートを制御する。DBはMySQL、PHPUnitのテストDBはSQLiteインメモリ。

リクエストはルート → 認証・初回設定・権限ミドルウェア → FormRequest → Controller → Service／Model → BladeまたはJSONへ流れる。検索・CSV取込・履歴同期は `Services/Opnavi` に配置する。

### 7.2 主要データ

| テーブル | 主な役割・関連 |
|---|---|
| `users` | 氏名・メール・ハッシュ化パスワード・権限・有効フラグ・初回設定フラグ・初期パスワード期限 |
| `opnavi_customers` | 事業者情報、`owner_id`（コール担当）、`sales_owner_id`（営業担当）、ステータス、次回日時、重要アラート、営業メモ、論理削除日時 |
| `opnavi_ota_links` | 顧客に紐づくOTA名と掲載URL |
| `opnavi_activities` | 顧客・登録ユーザー・対応日時・Rank・相手担当者・担当ステータス・ステータス・メモ |
| `opnavi_daily_call_results` | ユーザー別の日次確定スナップショット。日付、合計、JSON内訳、確定日時。ユーザー＋日付が一意 |
| `opnavi_customer_phone_indexes` | 顧客・電話カラム・3桁以上の電話部分文字列。電話の中間一致用 |

顧客1件に複数の履歴・OTAリンク、ユーザー1人に複数の担当顧客・履歴・日次成績が紐づく。コール担当と営業担当は別外部キーで管理する。

### 7.3 検索用インデックス

- MySQL: `business_name, address, sales_memo` の複合FULLTEXT。現在の `app/` マイグレーションには `WITH PARSER ngram` 指定がない。日本語のngram検索を前提とする場合、配備先の実際のインデックス定義を確認する必要がある。SQLiteではこの全文索引を作成せず、文字検索はLIKEに分岐する。
- 電話: 数字正規化カラムごとのINDEX、部分文字列テーブルの `phone_token` INDEX・顧客ID INDEX・重複防止UNIQUE。
- Rank／最新履歴: `(customer_id, action_at, id)` と `(customer_id, rank, id)` のINDEX。
- 電話索引の同期はCustomerモデルの保存イベントで実施する。モデルイベントを通さない直接SQL更新では、索引データの同期を別途行う必要がある。

## 8. 現在の制約・今後の判断事項

以下はコードから確認した現状であり、追加機能の実装を示すものではありません。

- 自己操作のパスワードリセット、MFA、個別のログイン試行回数制限はログイン処理にない。忘れた場合は管理者の初期パスワード再発行を利用する。
- 招待時の手入力初期パスワードは、画面に「英数字混在」と表示されるが、サーバー側は最低8文字のみ検証する。英数字混在が必須なのは初回設定と通常変更。
- 無効化チェックはログイン時に行う。権限ミドルウェアは `is_active` を確認しないため、ログイン済みセッションの即時停止は未実装。
- 初期パスワード期限はログイン時に検証する。初回設定POSTで期限を再検証する処理はない。
- 営業／アポイントは担当顧客内の他ユーザー作成履歴も更新でき、更新時には履歴の `user_id` が操作ユーザーへ置き換わる。本人の未確定成績が変化し得るため、履歴編集権限・登録者の保持方針は検討対象。
- 初期パスワード再発行は期限切れユーザー以外にも実行可能。ユーザー再有効化・物理削除の管理画面はない。
- 営業担当の基本情報UIは選択不可だが、管理者の顧客更新リクエストは `sales_owner_id` を受け付ける。APOポップアップだけに変更経路を限定するサーバー制約はない。
- CSVから自動作成する担当者ユーザーは既定ロール等に依存するため、3権限のログイン運用に使う場合は招待ユーザーとの対応付けが必要。
- MySQLのFULLTEXTはパーサー・最小トークン長・ストップワード設定の影響を受ける。現在のマイグレーションではngramが指定されていないため、過去の要件や実DBとの差を確認する必要がある。SQLiteテストだけではMySQL固有の一致結果・検索性能を検証できない。

認証情報・SMTPパスワード・実アカウントの初期パスワードは本書に記載しない。設定値は環境別に管理する。
